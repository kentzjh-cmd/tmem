# 独立场景端到端验证：tmem 在真实 DSH 项目上的效果报告

> **研究类型**：受控对照实验（预注册假设 + 三条实验臂 + 机器可读判定 + 修复前后对照 + 两轮复验）

> **被测对象**：与 tmem 仓库**完全无关**的合成真实项目 `ledger-svc`（Python 发票台账服务）
> **规模**：Round 1 共 11 场真实 `dsh headless` 模型会话（实验组 8 + 对照组 3）+ 1 组纯 CLI 检查；Round 2 共 **17 场**真实模型会话（A 臂 9 + C 臂 3 + B 臂 5）+ 1 组纯 CLI 检查；另加披露式记忆专有探针 H6′ 的 6 个变体

**本次研究新发现并修复 5 个真实缺陷**：N1 中文自然语言 `tmem lookup` 完全失效（P1，修复前 0/8 命中，修复后 7/8）；N2 注入遥测盲区、N3 归因跨会话泄漏、N4 跨工作区 transcript 误取（均已修复并加回归测试）；**N12 工作区安装的插件"半挂载"**（自动注入有效，但 `tmem_search`/`tmem_expand` 永不注册，且工作区安装会覆盖全局完整安装——按官方文档安装的典型场景即受影响），已修复并有红/绿对照回归测试（全量测试 53 → **62 全绿**）。另记录 2 项**装置级缺陷**（N11 被测 agent 自行 `tmem init`、N13 装置脚本重复还原全局 patch）与 3 项已知边界（N8/N9/N10）。

## 2. 方法

### 2.1 为什么另造场景

上一轮战役的所有轨迹侧验证都基于 `/archive/tmem` 自身的 `.tmem/` 数据——用被测工具自己产生的、又在同一套代码库上产生的数据去证明同一个工具正确。这是**自证循环**，且既有验证**从未检验"记忆是否真的被模型消费"**（只验证到"记忆被生产出来"）。本研究同时破除语料偏差（换语言、换领域）、形态偏差（用 DSH 原生多帧 transcript）、规模偏差（多会话、跨增量），并补上消费侧这一跳。

### 2.2 被测项目 `ledger-svc`

由 `/home/kent/e2e/_harness/build_fixture.py` 全自动生成（可复现）：

- 15 个 Python 源文件 + 5 个测试文件，21 个 pytest 用例（基线 3 failed / 18 passed）
- 46 次提交（main + 2 特性分支 + 2 次 `--no-ff` 合并），2 处重命名（`ledger_store.py→store.py`、`http_api.py→api.py`）
- 共变关系用 **append-only 语义**生成，保证每个"共变提交"都是真实 diff

**植入缺陷**（错误签名互不相同，可从外部观察）：

| 编号 | 位置 | 外部症状 | agent 的实际修复 |
| :--- | :--- | :--- | :--- |
| D1 | `src/ledger/settlement.py` | `ValueError: cannot convert NaN to integer` | 新增 `money.ensure_valid_price()` + `ValidationError` 显式拒绝 |
| D2 | `src/ledger/rates.py` | `KeyError: 'USD:CNY'` | 缓存未命中回落到 `DEFAULT_RATES` |
| D3 | `src/ledger/pagination.py` | 断言失败：同秒创建的发票翻页被漏 | 游标改按发票序号（sequence）排序 |

**预埋共变结构**：5 条正样本对 + 3 条负样本对（从不一起改动，用于测精确率）。

### 2.3 实验装置：三条臂

第一轮 S1 暴露了一个必须处理的混淆因素：

> **实验中途观察**：在 S1（tmem 组）里，agent 不仅调用了记忆功能，还**自行把业务约定写进了 `AGENTS.md` / `README.md` / `MEMORIES.md`**。
> 若只比较"有 tmem"与"无 tmem"，观测到的召回差异可能来自**agent 自记笔记**，而不是记忆插件。

于是实验扩充为三条臂：

| 臂 | 工作区 | DSH 插件 | 先前会话 | 作用 |
| :--- | :--- | :--- | :--- | :--- |
| **A** | `ledger-svc` | ✅ | ✅ | 主实验：完整记忆闭环 |
| **B** | `ledger-svc-control` | ❌（全局 patch 临时摘除 tmem 条目） | ✅ | 分离"agent 自记笔记"的贡献 |
| **C** | `ledger-svc-control` | ✅（插件在、记忆库空） | ❌ | 基线：题目本身可答性 |

> **协议修订（执行中披露）**：原设计把 B 定义为"无插件"，但执行中发现全局 `~/.dsh/cordis.patch.yml` 带有 tmem 插件条目，使所有会话都加载插件。为得到真·无插件臂，B 臂改为在执行期间**临时摘除全局 patch 的 tmem 条目**（脚本内 trap 保证无条件还原，还原后 diff 校验一致）。C 臂则保持"插件在、记忆库空"，它其实是更严格的基线（把插件恒定住，只测记忆内容）。该修订在结果章节中显式给出，不隐藏。

> **Round 2 的加固（追加披露）**：B 臂先后两次失效，归因见 §3.11。最终采用的 B 臂条件是：**home patch 的 tmem 条目被摘除且运行期间只读** + **对照臂禁用 `tmem init`** + **每场前后逐项断言**（无 tmem 工具、无注入块、工作区无 `.dsh/`）+ **写入归因 watcher**。B 臂的作用因此从"粗粒度地没有插件"升级为"**逐场可证明**没有插件"。

### 2.6 已知混淆与局限（事前声明 + 执行中修订）

1. **模型非确定性**：单场单次观测。受控措施：三臂同模型同题；H6 的三道题按"是否可在无记忆时答出"分层；严格/宽松两套关键点分别报告。
2. **题目自记泄漏**：agent 会把结论写进仓库文件 → 由 B 臂显式测量并从因果链中扣除，而非假设其不存在。
3. **合成项目偏真**：fixture 贴近真实但非生产代码；H4 检验的是"能否还原已知结构"，不是真实仓库的先验准确率。
4. **S6 前提被上游改变**（执行中修订）：S2 里 agent 已顺手加固 `import_rows`，S6 的原始前提失效 → 追加 S6b 受控重演（脚本化注入同签名缺陷，已在 §3.7 披露）。
5. **agent 不提交时归因累积**：见 §3.2 与缺陷 N3。
6. **S7 的 expand 延迟含进程启动开销**（100ms 为端到端 wall-clock，非纯索引延迟）。

### 2.7 执行中披露：三项缺陷修复与 Round 2 复验

Round 1 判定完成后，对缺陷 N2、N3（及在复验中新发现的 N4）做了根因定位并**在本地修复**，随后**用同一套预注册协议、同一套场景剧本重跑了一遍完整实验（Round 2）**。两轮全部数据均保留，判定口径与修订全部公开。

| 项 | Round 1 | Round 2 |
| :--- | :--- | :--- |
| 被测代码 | `f03cdd2` + N1 修复 | `f03cdd2` + N1 + N2 + N3 + N4 修复 |
| 工作区 | `/home/kent/e2e/ledger-svc` | `/home/kent/e2e/r2/ledger-svc` |
| 原始证据 | `_harness/raw/` | `_harness/raw-r2/` |
| 判定结果 | `_harness/metrics.json` | `_harness/metrics-r2.json` |

**修订 1（测量口径）——G3 的归因聚合范围。** Round 1 的 G3 只读取 `capture.json` 里**最后一次手动 `tmem capture`** 的 `touched_files`。但一次 DSH 会话会产生多次捕获：hook 在验证通过后自动捕获，agent 还会在收尾时手动再捕获一次；而手动捕获是**增量**的（从上次捕获的 step 起），因此单看它会低报该会话的归因。

Round 2 的 G3 主判据改为 **`episode_union`**：该 DSH 会话**全部捕获事件**（episode，每次捕获写一条、**从不跨会话合并**）的 `touched_files` 并集。选 episode 而不是 trace 的原因是：playbook 会按相似度**跨会话合并**（缺陷 N7），合并后 `source_session_ids` 会列出多个会话、文件集也会求并，从而把别的会话的改动算进来；episode 不存在这个问题。

三种聚合范围在 `metrics.json` 的 `aggregation_scopes` 中**同时给出**（`episode_union` / `trace_union` / `single_capture_only`），阈值不变，**不做事后调参**。

**修订 2（测量口径）——精度分母排除插件内部路径。** `.tmem/**` 与 `.dsh/**` 是插件自身的存储与安装产物，不是项目代码；它们既不计入真值，也不计入精度分母，与真值口径保持一致。

**修订 3（产品修复）——三项缺陷本地修复并加回归测试**（`tests/attribution_scope.test.mjs`，4 例，红/绿对照已验证）：

- **N2**：`tmem/hooks/dsh.mjs` 的锚点召回注入路径补记 `l2_injected` 遥测；`tmem/telemetry.mjs` 增加 `source` 字段与 `l2_injection_sources` 汇总。
- **N3**：`tmem/slicer.mjs` 在**脏工作区**下把归因收窄到本窗口实际引用过的文件；**干净工作区**（会话已提交）仍保留提交级归因，行为不变。
- **N4**：`tmem/adapters/dsh.mjs` 的 transcript 发现优先选择路径编码匹配本工作区的会话。

> **边界声明**：Round 2 的每一场都是**重新发生的真实模型会话**，不是对 Round 1 数据的重放；两轮之间的差异同时包含"代码修复"与"模型非确定性"两个来源。因此 Round 2 与 Round 1 的差异**不能全部归因于修复**，只能作为方向性证据；结论以门槛判定（是否达标）而非数值微差为准。

### 3.5 H5：知识检索（G6）——**发现并修复真实缺陷**

| 检索路径 | 修复前 | 修复后 |
| :--- | :--- | :--- |
| `tmem lookup`（插件零 token 预检路径） | **0.000**（0/8） | **0.875**（7/8） |
| `tmem search`（倒排索引路径） | 0.625 | 0.625 |

**根因**：SQLite FTS5 的 `unicode61` 分词器把**一整段中文视为单个 token**。查询"汇率表定义在哪个文件"被切成单个 token，而索引里存的是"headless 结算取汇率时，缓存里没有这个币对就会抛 KeyError"这样一个整句 token → 短语查询永远匹配不上。仓库内自证验证之所以发现不了这个问题，正是因为那里的内容几乎全是英文标识符。

**修复**（本研究授权的本地修改，尚未提交）：`tmem/store.mjs` 增加 `cjkBigrams()`，查询侧对中文按**字符二元组覆盖**直接对已存 payload 打分（无需重建索引、对存量库即时生效）；新增回归测试 `tests/cjk_lookup.test.mjs`（2 例）。全量测试 **53/53 绿**。

唯一未命中的 F05（幂等键）是**真值设计问题**：整个实验没有触碰幂等模块，该主题从未进入记忆库（`search` 同样未命中），不是检索缺陷。

**Round 2 的 G6 = 0.625（低于阈值 0.70）——归因分析（重要）**：Round 2 的 F01（测试命令）与 F04（舍入策略）未命中，但 **F01 的答案确实在库里**（`tr_505fa46b28` / `tr_e27e3a933a` 的 intent 里写着"测试失败基线: PYTHONPATH=src python3 -m pytest"；`ROUND_HALF_UP` 出现在 `ep_737da275c5`）。实测对照：

| 查询 | 命中数 |
| :--- | :--- |
| `运行这个项目的单元测试用什么命令`（中文） | **0** |
| `pytest test command`（英文） | **3** |
| `PYTHONPATH=src python3 -m pytest`（直接给命令） | **3** |

根因是**措辞敏感 + 跨语言边界**：中文提问与库里的中文措辞只有 1 个二元组重合（"测试"），低于 `need = max(2, ceil(grams × 0.15))` 的阈值；Round 1 之所以能命中，是因为当轮 agent 的措辞里恰好有 ≥3 个重合二元组（"单元测试/命令/运行"）。**这不是 N1 修复的回归，而是"二元组词面匹配"这一确定性方案的天花板**（详见缺陷 N8）。

> **未修的理由（有意为之）**：跨语言/语义等价召回需要嵌入检索或手工中英词典，两者都违背 tmem "确定性、零 token、无外部模型"的设计前提。该边界已作为已知限制记录，并进入 Round 7 载体消融课题（见 [`docs/dsh-memory-carrier-ablation.md`](./dsh-memory-carrier-ablation.md) 的结构化检索指标）。

### 3.6 H6：记忆是否被消费（G7）——三臂对照

| 臂 | 宽松关键点（预注册） | 严格关键点（披露式修订） |
| :--- | :--- | :--- |
| A（插件 + 记忆 + 先前会话） | 1.00 | **1.00** |
| B（无插件 + 先前会话） | 1.00 | **1.00** |
| C（插件 + 空记忆 + 无先前会话） | 1.00 | **0.00** |
| A − C | 0.00 | **+1.00** |
| A − B | 0.00 | **0.00** |

**按预注册口径（宽松关键点）G7 = FAIL**：三臂全部 1.00，无判别力。原因是宽松关键点（"对账"、"上游"、"拒绝"、"校验"）会被**通用工程答案**命中——C 臂在完全无记忆的情况下仍给出了标准的账务工程理由，其中恰好包含"对账"一词。

**按严格关键点（披露式修订，追加多词关键点如"上游对账系统""只接受整数分""ValidationError""ROUND_HALF_UP"）**：

- **A − C = +1.00**：先前会话确实让模型能答出项目专属事实（Q01 上游对账约定、Q02 nan 价格校验策略），而 C 臂不能 → **"先前会话带来项目专属知识"成立**。
- **A − B = 0.00**：B 臂（无插件，但有 agent 自记的 `AGENTS.md`/`README.md`/`MEMORIES.md`）达到与 A 臂相同的召回。

> **⚠ 事后追查得出的重要更正（Round 2 复验期间发现）**：`A − B = 0.00` **不能**推出"插件对召回的边际贡献为 0"。逐题核查三个严格关键点的**可得性**后发现，它们**本来就不要求记忆**：
>
> | 题 | 关键点 | 无插件也能拿到该知识的路径 |
> | :--- | :--- | :--- |
> | Q01 | 上游对账系统 / 只接受整数分 | **就写在 S1/B1 的提示词里**（"因为上游对账系统只接受整数分"），B 臂收到的是**逐字相同的提示词** |
> | Q02 | ValidationError | **fixture 初始代码 `src/ledger/errors.py` 里就有 `class ValidationError(LedgerError)`**；B1 会话读过代码即可命名 |
> | Q03 | ROUND_HALF_UP | **代码里写着**（`src/ledger/money.py` 用 `ROUND_HALF_UP`），且 oracle 自身已标注 `answerable_without_memory: true` |
>
> 已核对对照组工作区的实际产物证实这一点——B 臂 agent **自己**写进 `README.md` / `AGENTS.md` 的是：
> - `README.md:12` "结算结果统一使用整数最小单位……**上游对账系统只接受整数分，这条约定不可变更**"
> - `AGENTS.md:51` "用例期望的是项目自己的 `ledger.errors.ValidationError`（`api.handle()` 只捕获 `LedgerError` 子类…）"
>
> 因此 B 臂的 1.00 来自"**提示词 + 自记笔记 + 读过代码**"，**不是来自记忆**。结论应改写为：
> - **G7（无论预注册口径还是严格口径）都没有测出"插件的边际贡献"**，因为关键点集不具备记忆专有性；
> - **G7 测出的是**：*先前会话*（无论其知识来自插件记忆还是 agent 自记笔记）能带来项目专属知识（A−C = +1.00），而*没有先前会话*就不能（A 严格口径 1.00 vs C 严格口径 0.00）；
> - 顺带暴露的测量缺陷：S5/C5 的提示词写着"**不要读代码，直接回答**"，这让**无先前会话**的 C 臂在 Q02 上被额外削弱（它连 `errors.py` 都没去读）；这是协议设计问题，不是插件问题。
>
> **对 Round 2 补跑的启示**：若要真正测出插件的边际贡献，探针必须满足"**答案不在提示词里、也不在初始代码里、只在先前会话的修复过程里**"——例如"上次那个 nan 价格的坑最后是怎么修的、根因落在哪一步、为什么不能用裸 ValueError"。这类问题只有经历过 S2 修复过程的 agent 才答得出。

**更关键的观察**：B 臂里 agent **自己发现了全局安装的 `tmem` CLI 并主动调用**（对照组工作区最终生成 2 条 trace、2 个 episode、`MEMORIES.md` 头部标注 "Maintained autonomously by tmem"）。也就是说：

- "把知识落到项目记忆里"这件事，**模型会自发去做**（写散文式笔记），这一层不是插件独占；
- 插件真正独占的是**回合级自动注入**（G8）与**提交钩子自动捕获**——这两项本报告已给出正面证据；
- 但要注意 B 臂**并非纯无插件基线**：全局 `tmem` CLI 仍在 PATH 上且被 agent 主动调用，B 臂测到的是"**无自动注入**"，不是"**无 tmem**"。

一个值得记录的正面细节：A 臂 S5 的回答里，agent 明确写道"**至于具体的舍入模式…项目记忆里没有写明**，这一条我不能替你断言"——它**如实报告了记忆的空白**，而不是编造。这是一个值得肯定的行为特征。

> **Round 2 收尾（披露式追加测量 H6′ 的结果）**：本节更正指出"G7 的关键点不具记忆专有性 → 边际贡献未测出"。Round 2 用**另立**的记忆专有探针（题目只存在于结构化记忆里，三臂逐字同题）补上了这一跳，结论是 **H6′-1 与 H6′-2 两个门槛均 PASS**：禁止读取时 A 臂 1.000 / B 臂 0.333 / C 臂 0.000；获取成本 1 742 token vs 无插件臂翻文件的 77 710 token（≈44.6 倍）。**预注册的 G7 仍按其原口径判为 FAIL**，两者并列报告、不合并、不替换（见 §3.12）。

### 3.7 H7：跨位置的修复迁移（G8）——插件独有能力

S6b 为**受控重演**：由脚本向工作区注入一个新模块 `src/ledger/bulk.py`，它以**修复前的写法**直接对 `nan` 价格做 `Decimal(...)` 运算，签名与 S2 完全相同（`ValueError: cannot convert NaN to integer`）。

结果：

1. **记忆块被自动注入到新一轮**——S6b 的 transcript 中出现 `<tmem_speculative_memory>`；
2. **注入块携带了完整的历史修复**，原文节选：

   > `[Trace tr_4c1d4e9195 | Tier: L0_FULL | Confidence: 0.90]`
   > `- Historical Intent: 约定(不可变): 缺失价格(空单元格被导出器写成文本 nan)必须用项目自己的 ledger.errors.ValidationError 显式拒绝, 不得抛裸 ValueError/KeyError(api.handle 只捕获 LedgerError 子类)。根因链: (1) import_rows.parse_price 只做 float(raw) 不校验 …`
   > `- Root Cause: Error 'ValueError' resolved by 'edit src/ledger/money.py (ensure_valid_price, format_money, is_missing_price) -> edit src/ledger/import_rows.py (…) -> edit src/ledger/settlement.py (settle_invoice)'`
   > `- Verified L0 Critical Path (Guards Passed): READ(src/ledger/import_rows.py) -> READ(src/ledger/settlement.py) -> READ(src/ledger/errors.py) -> READ(src/ledger/money.py)`

3. **修复在新位置被采纳**：`src/ledger/bulk.py` 最终采用 `ValidationError` / `ensure_valid_price` 模式。

这是**本研究中最强的一项正面结论**：同一错误签名在**新代码位置**复现时，插件把"上次怎么修的"（含根因链与验证过的 L0 关键路径）主动送进上下文，agent 直接复用。**B 臂（无插件）无法产生这一行为**。

**但有一个观测缺口（Round 1）**：该注入路径**没有产生 `l2_injected` 遥测事件**（`l2_injections = 0`），即"发生了注入"却"遥测看不见"→ 见缺陷 N2。**Round 2 已修复**：同一路径现在会补记 `l2_injected`（`source: "anchor_recall"`），Round 2 的真实会话中遥测首次出现非零注入计数。

### 3.11 对照臂两次失效的归因与装置加固（新增缺陷 N11 / N12 / N13）

Round 2 的 B 臂（"无插件 + 有先前会话"对照）先后**两次**失效：前半程干净、后半程被污染。本节记录完整取证链。它本身就是一项方法学结果——**"对照组没有插件"这个前提，既可能被实验装置破坏，也可能被被测 agent 主动破坏**，两者都必须用独立证据排除，不能靠假设。

#### 判定"插件是否挂载"的可观测量

一次 DSH 会话的 transcript 里有两个直接可读的观测量：

| 观测量 | 出处 | 含义 |
| :--- | :--- | :--- |
| `request/header` 的 `tools` 列表 | transcript `request/header` 事件 | 插件挂载时会带 `tmem_search` / `tmem_expand` |
| `user/message` 中的 `<tmem_speculative_memory>` | transcript `user/message` 事件 | 记忆块确实被投进了上下文 |

工具清单只覆盖"完整挂载"，注入块覆盖"实际生效"，两者合起来才足以判定一场对照会话是否干净。

#### 第一次失效（15:15 前后）：装置级竞态

- **现象**：按时间顺序审计控制臂工作区路径下的会话，插件挂载状态在 B2b 处**从"无"翻转为"有"**（15:15:28 起的三场全部带注入块）。
- **零 token 复现**（用无效 API key 让模型调用必然失败，只看会话启动时注册的工具）：home patch 含 tmem 条目 → 25 个工具（含 `tmem_search`/`tmem_expand`）；摘除后 → 23 个工具、无 tmem；**同一目录连续第二场结果相同** → 排除"陈旧 project cache"与"会话继承"两类假设（`~/.dsh/storages/session_projcache` 只存会话状态，不含插件解析结果）。
- **排除 tmem 自身**：全仓只有 `tmem init` 会写 home patch（`tmem/installer.mjs:173-189` ← `tmem/cli.mjs:412`）；B1 里唯一一次 `tmem init --help` 的输出是**通用 usage 帮助**而非安装器 JSON，未执行安装。
- **并发实例**：中止时的残留进程清单同时包含 `bash run_b_arm.sh` 与 `python3 run_scenes.py --scenes B1…,H6_probe_b_free`，即**两个 B 臂实例并存**。
- **trap 语义**：`trap restore EXIT INT TERM` 在收到 SIGTERM 时会**触发两次**还原（信号处理 + 随后的 EXIT），复现输出见 `_harness/trap_test.out`（两次时间戳相差 3 ms）；两次实例又**共用同一个固定 BAK 路径** `$H/cordis.patch.yml.bak`。
- **结论**：被中止实例的迟到 EXIT 还原，把"含 tmem 条目"的备份写回 home patch，正好落在 B5 结束（15:15:25）与 B2b 开始（15:15:28）之间的 3 秒窗口内。

#### 第二次失效（22:46 前后）：**被测 agent 自主执行了 `tmem init`**

在加固装置后重跑时，装置自己的前置断言拦下了第二次失效（22:46:45，`[b-arm] FATAL: tmem entry present ...`）。逐条核查 B1 的 **57 次工具调用**后得到两条结论：

1. **在更早一轮（22:34:06）里，同一个机制被直接观测到**：对照臂 agent 自己执行了 `tmem init`，installer 随即写出 `<workspace>/.dsh/tmem.patch.yml` + `.dsh/plugins/`（工作区层）**与** `~/.dsh/cordis.patch.yml`（home 层），从下一场起插件被挂载并注入记忆。**这是"被测 agent 会主动把插件装上"的首次直接观测**——比 N6（agent 主动写散文笔记）更进一步：它不是写笔记，而是**改变了实验装置**。
2. **隔离实验证明只有 `tmem init` 会写 home patch**：`capture`（含 `--full-session` / `--force`）、`sync`、`status`、`list` 在隔离 `DSH_HOME` 下逐一试过，home patch 的 tmem 条目数始终为 0。

因此对照臂的失败**不能**简单归结为"装置写错了"，而必须处理 agent 主动安装插件这一行为。

#### 第三层问题（N12）：工作区安装的插件是**半挂载**的

追查"为什么 22:46 的写入没有出现在 B1 的工具调用里"时，发现了一个**独立的产品缺陷**：

| 挂载方式 | 插件来源 | 自动注入 | `tmem_search`/`tmem_expand` | tmem 系统提示 |
| :--- | :--- | :--- | :--- | :--- |
| home 层（绝对路径 `/archive/tmem/tmem/dsh_plugin.mjs`） | 包本体 | ✓ | ✓ | ✓ |
| 工作区层（`tmem init` 写出的独立副本 `<ws>/.dsh/plugins/tmem-dsh-plugin.mjs`） | 副本 | ✓ | **✗** | **✗** |

机制：独立副本旁没有 `hooks/`、也没有 `cli.mjs`，而 `import("dsh-tmem/hooks")` 从该目录出发**无法解析**（全局 npm root 不在 Node 的模块解析链上，实测 `ERR_MODULE_NOT_FOUND`）→ `loadInProcessRuntime` 返回 null → 插件降级为 CLI 兜底（`tmem hook dsh`）：**hook 照常工作（注入照常发生），但 `createTmemTools` 不可用，两个模型可见工具永不注册，tmem 系统提示段落也缺失**。

更关键的是：`--patch` 的工作区条目与 home 层条目 **id 同为 `tmem`、且工作区条目后应用**，所以工作区安装会**覆盖**全局完整安装 → **按官方文档 `tmem init` 安装的典型场景，模型拿到的是半挂载插件**。本研究的 A 臂（实验组）正是这种安装方式（23 个工具、无 tmem 工具），因此 A 臂享受的是"回合级自动注入"，而**没有**按需检索工具（agent 实际是用 bash 调 `tmem search` 走 CLI）。

#### 装置加固（已实施）

| 层 | 措施 | 作用 |
| :--- | :--- | :--- |
| 1 | `flock` 独占锁 | 杜绝并发实例（第一次失效的根因） |
| 2 | BAK 改为 `mktemp` 唯一路径 + `trap 'restore' EXIT` 单次还原 | 杜绝备份互覆与双重还原 |
| 3 | **封禁对照臂的 `tmem init`**（PATH shim，只挡 `init`，其余子命令可用） | 挡住"agent 主动安装插件" |
| 4 | 装置运行期间 home patch **只读（444）** | 即使绕过 shim 也写不进去 |
| 5 | 每场**前后**断言：无 tmem 条目、工作区无 `.dsh/`、该场无 tmem 工具、无注入块 | 污染即刻中止，不再静默产出脏数据 |
| 6 | `watch_patch.py` 后台 watcher（30 ms 轮询 + `fuser`/`lsof` 归因） | 写入可归因 |
| 7 | 清除对照臂工作区里由 `tmem init` 留下的 `.git/hooks/post-commit` | 否则对照臂一次 commit 就会触发 tmem 捕获 |

加固后 B 臂重跑结果见 §3.12。

### 5.3 对产品定位的含义

tmem 的价值不应表述为"帮 agent 记住东西"——模型自己会写 `AGENTS.md`。更准确的定位是：

1. **跨位置的因果修复迁移**（G8）：把"上次怎么修的"送到新位置，这是 agent 自己做不到的；
2. **零 token 的结构化检索**：共变拓扑、错误签名→修复对、验证过的 L0 路径，可被程序化消费（前提是修好中文检索，N1）；
3. **自动捕获与提交钩子**：把会话变成机器可读的工程资产。

### 5.4 由此立项的后续研究课题

§3.6 的更正暴露出一个方法论缺口：**本报告没有测出"载体"（结构化记忆 vs 散文式 MD）的独立效应**，因为 agent 自记笔记把载体差异遮蔽了。由此立项：

> **载体消融与量化研究课题** —— 在知识内容**完全相同**的前提下，比较 tmem 结构化记忆 / 散文式 MD 记忆 / 无记忆，在 **token 成本**、**任务效果**（含同签名复发率）、**结构化独有能力**（共变提示、错误签名→修复对）三组指标上的差异。
>
> **三个因子**：载体（tmem 结构化 / 散文式 MD）× 获取方式（自动注入 / 按需读取）× **上下文压缩（压缩 / 不压缩）**；**定性与定量并重**——压缩专项除"记忆存活率 / 重注入缺口 / 索引展开率 / 压缩后复发率 / 知识找回 token"等定量指标外，配一套**可双人独立编码的行为编码表**（Q1 正确复用 / Q2 部分复用 / Q3 失忆重踩 / Q4 索引未使用 / Q5 索引未送达 / Q6 通知冗余 / Q7 注入未重放），并要求两类结论交叉验证。
>
> 预注册门槛 CA-1..CA-9，每臂 ≥3 次重复。
>
> 追查该课题时发现一个**待确认的产品缺陷**：`tmem/hooks/dsh.mjs` 的 `state.injected_trace_ids` **只增不删**，上下文压缩后不会重新注入此前给过的历史修复——而压缩摘要极可能已把它从 live context 抹掉。该缺口已作为假设 **H-F** 与消融臂 **C4** 写入课题。

课题设计、指标定义、控制变量与已知陷阱清单见 [`docs/dsh-memory-carrier-ablation.md`](./dsh-memory-carrier-ablation.md)。

### 5.5 结论边界（不可外推的部分）

- 合成 fixture 的共变结构是**设计出来的**，H4 证明的是"能还原已知结构"，不是真实商业仓库上的先验准确率；
- 单场单次观测，未做多次重复采样，模型非确定性的影响未被量化；
- G7 的严格口径是**执行后追加**的修订（预注册口径为宽松口径，且按其判定为 FAIL）；
- H6′ 的三道题是**单次观测**，且题目与 fixture 强相关；它证明的是"记忆专有事实可经注入被消费且成本更低"，不是效应量的稳定估计；
- B 臂的"无插件"依赖临时修改全局 patch，且 Round 2 证明该前提**会被被测 agent 主动破坏**（agent 自跑 `tmem init`）；Round 2 的最终数据来自加固后的装置（只读 patch + 封禁 init + 每场断言 + 写入归因 watcher），但这一依赖仍然是**方法学上的脆弱点**；
- Round 2 的 A 臂数据采集于 N12 修复**之前**（当时插件为"半挂载"：注入有效、`tmem_search`/`tmem_expand` 未注册）；修复后 A 臂需重跑，两批数据不可混用。

## 6. 结论

1. **tmem 在与自身无关的真实项目上是可用的**：6 场有工作量的真实会话全部编译出轨迹，真实编辑文件召回 1.000，3 个错误签名全捕获，共变结构 recall/precision 双 1.000。
2. **上一轮的两个 P0 已由远端真正修复**：多帧 zstd（11/11 真实 transcript 逐帧一致）与 CI 延迟门（10/10 全绿）。
3. **插件最硬的能力是"跨位置迁移修复"**：受控重演中，历史修复被主动注入并在新位置被采纳，且注入块携带完整根因链与验证过的 L0 关键路径——无插件臂无法复现。
4. **"记忆被模型消费"这一跳的插件边际贡献，在预注册口径下仍未测出（不是测出为零）**：G7 的三道题分别来自提示词、fixture 初始代码与代码本身，**本就不要求记忆**，A−B=0.00 无法归因于插件；**Round 2 用另立的记忆专有探针（H6′）首次测出**：禁止读取时 A 臂 1.000 / 无插件臂 0.333 / 空记忆臂 0.000，且注入式获取 **1 742 token** vs 无插件臂翻文件 **77 710 token（≈44.6×）**。插件**已证明独占**的能力是自动注入与自动捕获。
5. **发现并修复 5 个真实缺陷**：N1 中文自然语言 `tmem lookup` 此前 0 命中，修复后 0.875；N2 注入遥测盲区、N3 归因跨会话泄漏、N4 跨工作区 transcript 误取，均已修复并加回归测试；**N12 工作区安装的插件"半挂载"**（注入有效但 `tmem_search`/`tmem_expand` 永不注册，且会覆盖全局完整安装）已修复并有红/绿对照回归测试（全量测试 53 → **62 全绿**）。
6. **修复在 Round 2 复验中已取得可测量的效果**：会话级归因精度 **0.796 → 0.846**（同口径；S2/S3/S4 三场的 precision 均为 1.000，跨会话泄漏归零）；注入遥测 `l2_injections` **0 → 12**（Round 1 的盲区闭合）；G3/G4/G5/G8 均 PASS。
7. **Round 2 已跑完**：预注册门槛 **6/9 通过**（G1/G6/G7 未过，原因分别是纯 Q&A 会话无可捕获动作、跨语言检索边界、关键点不具记忆专有性，均为已知边界而非插件失败）；**披露式追加测量 H6′ 的两个门槛全部通过**。
8. **一项方法学结论值得单独记下**：本轮对照臂曾两次失效——一次是装置脚本在并发/中断下重复还原全局 patch（N13），一次是**被测 agent 自行执行 `tmem init` 把插件装回对照臂**（N11）。因此"无插件对照"必须逐场断言（工具清单 + 注入块），不能靠配置意图；Round 2 最终数据来自加固装置且 watcher 记录到运行期间零意外写入。
9. **Round 3 用修复后的插件重生成主数据集：预注册门槛 7/9 通过**（Round 2 为 6/9）。唯一的门槛级变化是 **G6 由 FAIL 转 PASS**（lookup 0.625 → 0.75），归因指认到上游提交 `8238202` 的 CJK 2 字查询 gram 阈值修正；**G3 归因精度 0.846 → 0.908**；G1 与 G7 仍按原口径判负；B 臂 5 场全部 CLEAN。H6′ 探针在 23:10 被 429 打断后于 00:01 配额重置时自动补齐，**两个门槛均 PASS**（可得性 0.333 vs 0.000/0.000；成本 1 874 ≤ 0.30 × 25 408）；A_zero 命中率的下降已归因到**探针与播种内容脱钩**，而非插件能力下降。
10. **载体消融课题已完成（Phase-1b 隔离重跑，30/30 场有效、零越界读取）**：门槛 **2 / 5 通过**——CA-5（载体等价）与 CA-E1（效果优势：zero 变体 A1 1.000 vs C 0.000、B2 0.000）通过；CA-1 / CA-1b / CA-4 三个**成本**门槛未通过。**对插件效果的最终判断：tmem 的收益是「零检索可得」与「注入块更小」（注入/翻文件 = 0.2736，两阶段独立复现 0.2738），不是「总上下文 token 更少」**——允许自由查阅时，tmem 臂的总知识获取成本（18 017 token）是散文翻文件臂（5 073 token）的 3.55 倍，因为 agent 会继续 `tmem_expand` 展开细节（carrier 类读输出 16 169 token）。§3.13 里"注入比翻文件省多少倍"的比值因此**只应在注入口径下引用**，不可当作总成本主张。
11. **三项方法学教训值得单独记下**：(a) **同一 UID 下 chmod 不是隔离**——属主随时能 `chmod` 回去，Phase-1 的对照臂正是这样越界读了别的实验的记忆库；结构性隔离只能用**挂载白名单**（容器），并逐场自动断言（越界读取自动作废）；(b) **注入节奏必须两侧对齐**——散文注入器每步注入一次会把"比载体"的门槛测成"比注入次数"（CA-1b 比值 1.22 → 2.53）；(c) **编译产物是记忆泄漏通道**——`.pyc` 里留着修复后代码的字符串常量，复位工作区必须 `git clean -fdx` 而不只是 `git checkout -- .`。两阶段门槛判定**逐项一致**，说明装置缺陷与结论错误可以分开。
